## 1. 目标与依据

**只实现纯 GPT Direct，不接入 π₀.₅ 或其他学习策略，不训练机器人策略。** GPT 负责动作决策；固定执行层负责校验与转换；机械臂控制器负责插补和伺服。

| 来源 | 采用内容 | 边界 |
| --- | --- | --- |
| [银河通用 GPT-as-Policy][1] | Astra Direct 的观测、动作与反馈机制 | 仓库 `gpt_only` 不启动 π₀.₅，只参考这个分支 |
| [Awesome-Astra-Embodied-AI][2] | 案例索引及原始出处 | 不是独立算法或统一控制系统 |
| [RoboDojo GPT-6 Astra Evaluation][3] | L3：GPT 通过固定、非学习的 Harness 控制机器人 | 动作链路中没有 VLA，与银河通用是独立项目 |

首个任务建议为“将桌面一个方块放入指定区域”。这是单臂实物方法迁移，不是原始双臂基准的等价复现。不同项目的接口和实验结果分别引用，不混用。

## 2. 系统如何工作

```text
任务 + 机器人说明 + RGB 图像 + 当前状态 + 历史反馈
                         ↓
           GPT 决定下一次末端位姿和夹爪目标
                         ↓
          固定执行层：约束检查、转换、SDK 执行
                         ↓
          新图像 + 实测位姿 + 误差 / 失败原因
                         ↓
                GPT 判断结果并继续调整
```

- GPT 决定接近、下降、夹取、抬升、搬运、释放和重试，不提供预写的 `pick(object)` / `place(target)` 宏。
- 每轮执行一个受限动作片段，结束后重新观察；模型推理期间不继续执行旧动作。
- 保留文字历史和执行结果；图像先保留最近两轮，参考 RoboDojo 的上下文设置。[3]
- 指令被接收不代表到达，夹爪关闭不代表抓取成功，GPT 自报完成不代表任务验收通过。
- GPT 不承担高频电机伺服。首版使用 SR4-C 非实时 SDK，不照搬上游仿真的 25 Hz 控制周期。

部署：Windows 仅通过 SSH 访问 `embotic@192.168.0.10`（别名 `gpt-for-policy`）；开发和闭环运行位于 Ubuntu 的 `/home/embotic/gpt-for-policy`。USB 相机和 USB 夹爪直接连接 Ubuntu。Ubuntu 与机械臂控制器 `192.168.0.160` 连接同一台路由器、处于同一网段，Ubuntu 当前经有线网卡 `enp2s0` 访问控制器。SSH 将 Ubuntu `127.0.0.1:17890` 反向转发至 Windows 代理 `127.0.0.1:1111`，远端 SSH shell 自动配置代理环境；机械臂通信直连。模型调用由 Ubuntu 发起，依赖 Windows 代理与承载转发的 SSH 连接持续可用；具体模型入口、权限和调用仍待验证。

## 4. 最小实现

以下为拟实现模块，不代表文件已经创建。

| 模块 | 职责 |
| --- | --- |
| `robot_adapter.py` | 独占 SDK 连接；读状态、执行受限目标、控制夹爪、停止并报告实际结果 |
| `camera.py` | 获取图像、相机 ID 和时间戳；检查图像是否过期 |
| `policy.py` | 组装任务、观测和历史，调用 GPT，解析结构化动作 |
| `run_episode.py` | 串行运行闭环；限制轮数和时长；保存图像、动作及执行日志 |

### 观测与动作约定

- **观测**：RGB、时间戳、六轴关节角、当前 TCP 位姿、夹爪状态、操作状态、上次执行结果。若夹爪只有命令值，明确标为命令值。
- **动作**：`request_id`、`position_m[3]`、`quaternion_wxyz[4]`、夹爪目标；另提供放弃入口。这是本项目拟定的单臂接口，参考银河通用 Direct 的位姿表达。[4]
- **坐标**：统一为机械臂基坐标系下的已标定 TCP。向 GPT 说明坐标轴、桌面位置、工具几何和活动范围，不能沿用 X5 的 link6 偏置。
- **转换**：SDK 边界按实际接口转换参考系及姿态；使用 `endInRef` 时确认参考系关系。用已知位姿验证，不把四元数当欧拉角。
- **反馈**：区分拒绝、已接收、执行中、到达、失败和超时，返回实测位姿及到达误差；取得执行后图像再开始下一轮。

RGB-only 起步，由 GPT 根据图像和机器人说明估计动作。如果增加深度或显式物体三维定位，记录为增强版本，不能与 RGB-only 结果混淆。

### 固定执行层边界

执行端独立校验参数、姿态、单步增量、速度、关节范围以及路径与桌面/障碍的关系。限值经现场验证后固定，GPT 不可修改。非法目标拒绝并返回原因，不静默改成另一个动作；执行层可做插补，但不代替 GPT 选择抓取点或任务步骤。

一次只执行一个运动请求；断线或超时后先确认实际状态，不自动重发。任务期间持续持有连接，避免每轮重连；SDK 断开接口可能停止运动，退出流程需明确处理。

## 5. 实施顺序与验收

| 阶段 | 工作 | 通过条件 |
| --- | --- | --- |
| 0. Ubuntu 运行环境 | 迁移项目和历史记录，配置 SSH；准备 Linux SDK、Python 环境并适配加载逻辑 | 免密访问和文件迁移可核对；SDK 导入及空闲状态下连接验证另行完成 |
| A. 硬件与坐标 | 核对示教器、工具、负载、安装，接入相机和夹爪 | 读数和参考系一致，图像可用，夹爪指令与实物一致 |
| B. 执行层 | 人工指定小幅目标，验证到达、拒绝、停止和超时 | 误差满足预先确定的容差，失败后不继续运动 |
| C. GPT 空跑 | 输入真实观测，仅保存模型动作，不执行 | 格式、单位和夹爪语义正确，不合法目标被拒绝 |
| D. 单步闭环 | 现场监督下执行一次 GPT 动作，返回新图和误差 | GPT 能依据实际结果调整下一步，记录完整 |
| E. 完整任务 | GPT 自主完成单方块搬运，保留现场停止能力 | 无人替它选择动作，成功、失败或放弃均可追溯 |

初期可固定向下抓取姿态，先验证位置和夹爪闭环，再开放姿态控制；明确记录这是受限版本。阶段 B 的人工目标只用于检查执行层，不作为阶段 E 的预写任务程序。

工程验收建议：5 个不同初始位置，每个重复 3 次，统一任务和预算；记录成功率、耗时、调用次数、拒绝次数及人工干预，失败也计入结果。成功由录像或人工复核物体已释放在目标区域且稳定。该协议是本项目建议，不是论文协议。

**当前第一步：完成 Ubuntu 的 Linux SDK 加载适配，接入 USB 相机和夹爪，再验证固定姿态的 TCP 小步运动；随后接入 GPT 空跑与单步闭环。** 历史关节点动验证不能替代笛卡尔执行层验证。RoboDojo 报告记载了实机测试因危险动作及硬件损坏而中止，不能将仿真表现视为实物可靠性证明。[3]
